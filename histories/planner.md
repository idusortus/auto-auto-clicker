- 2026-09-28: The animation seam is a pure `/web` concern: the engine emits an ordered `GameEvent[]` batch per rAF frame, the theme owns only the slot-to-cue mapping and presentation durations, and the renderer owns coalescing + a bounded transient-effect timer. The contract can validate animation without new text limits because it contains only token slot names and numeric durations. Reduced motion must gate both the existing CSS `@media` block and the new JS frame-swap logic; the observable invariant is that sprite `src` never changes to an animation frame when the preference is active.
- 2026-09-28: The enemy roster currently has a dual representation in `engine-core/src/content.ts`: per-enemy descriptive curves (`baseHp`, `hpGrowth`, `baseGold`, `goldGrowth`) and live factors (`hpFactor`, `goldFactor`) that scale global canonical helpers from `balance.ts` (`enemyMaxHp`, `goldReward`). The canonical helpers are the old global source of truth and are read only by `content.ts`; the per-enemy curves are read only by tests. Replacing the dual representation with real per-enemy curves removes the cycle-mean-1 normalization that previously kept pacing inside ±20% without touching `balance.ts`, so a measured multi-seed re-tune is unavoidable. The live wrappers must stay in `content.ts` (not `balance.ts`) to preserve the acyclic graph; `balance.ts` already imports `isBoss` and `BALANCE` from `balance.ts`, so putting `enemyForStage` in `balance.ts` would create a `balance ↔ content` cycle. `ACTIVE_THEME` is currently `lucky` in `engine-core/src/theme/index.ts:40`, which contradicts several docs that still describe `fantasy` as the active default; the doc reconciliation must reflect this.
- 2026-09-28: **CORRECTION — the configuration described in the entry above is now HISTORICAL.** The dual representation (descriptive curves + live `hpFactor`/`goldFactor`) was replaced by a single source of truth: each enemy owns its REAL `baseHp`/`hpGrowth`/`baseGold`/`goldGrowth` and its own `bossHpMultiplier`/`bossGoldMultiplier`; the factors and `bossStageInterval` are deleted. The re-tune was done — a ~4,415-candidate measured search produced the shipped roster, landing canonical **6.22 / 55.52** with all 5 seeds inside tolerance. Lesson for future planning: the load-bearing constraint is the GROWTH BAND, not the archetype grouping — per-enemy `hpGrowth` values must stay in ~±0.003 (shipped band 1.4273–1.4336) or the round-robin aggregate drifts the pacing proof. The search's archetype grouping was a search dimensionality aid only; the shipped roster has 12 individually-tuned values and `archetype` is inert.
