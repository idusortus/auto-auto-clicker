- 2026-09-27: Ran the slots+achievements feature as 3 phases (engine mechanics → balance retune → sim-policy fix + achievements/splash) on top of the archived v2 prototype. `askUserQuestion` was skipped correctly: the user had already chosen the sequencing ("achievements + crit rings + gold/QoL necklaces first; armor/enemy-attacks as a separate project; luck-beats-a-boss as a third decision"), so the orchestrator just executed it. Lesson: when a prior turn already settled the forks, don't re-ask — decompose and go.
- 2026-09-27: THE key catch of this feature — Phase 2 passed the pacing sim by tuning `SLOT_DROP_WEIGHTS`, but instrumenting it showed the sim NEVER equipped a ring or necklace (they have `dpsFactor=0`, so their candidate DPS tied the unarmed base and the DPS-only policy ignored them). Green gates were therefore proving something DIFFERENT from what the feature does, and the untested path (a real player equipping multiplicative crit/power bonuses scaled by an exponential item-level curve) was the runaway risk. Lesson: when a feature adds a metric dimension the harness does not model, "all gates green" can be a false negative — audit whether the sim's POLICY can even reach the new code, not just whether the code runs.
- 2026-09-27: Enforced the same rule as the earlier economy round: the sim's blind spot was fixed by generalizing its equip policy to a per-slot power score built ONLY from engine getters, plus a `bonus-gross` attribution term, and the reviewer independently PROVED sensitivity by zeroing the ring/necklace factors (canonical soft shifted 5.97→6.55 min). Lesson: a claim that "the harness now covers X" must be demonstrated by a perturbation test, not asserted in a report.
- 2026-09-27: Reviewer missed a real latent hazard the orchestrator then found: `state.ts → achievements.ts → state.ts` was a genuine ES-module import cycle (functional only because both refs resolve at call time). Fixed by extracting `gear-stats.ts` a leaf module (imports only balance/content/types) that both can depend on, then verified with a DFS over every relative import edge → CYCLES: NONE, and confirmed sim output byte-identical via a scratch baseline diff. Lesson: reviewers validate against the brief; the orchestrator should still spot-check structural properties (cycles, import direction) that no requirement names explicitly — and prove the fix with a differential test, not by inspection.
- 2026-09-27: Caps precedent worth reusing — crit/gold/power bonuses are clamped on the AGGREGATE in the getters (`CRIT_CHANCE_CAP 0.75`, `CRIT_MULTIPLIER_CAP 1.18`, `POWER_MULTIPLIER_CAP 0.02`, `GOLD_MULTIPLIER_CAP 0.25`), never per item, so every consumer (sim/web/projection) inherits the bound for free. This is what let the exponential drop curve stay the primary lever while multiplicative bonuses stayed bounded; documented as the kill-switch for late-game explosion.
- 2026-09-26 (verification turn): Confirmed `sim/src/sim.ts` imports ONLY the engine-core root and references no persistence API (no saveGame/loadGame/SaveRepository/localStorage/JSON) — it is a pure in-memory tick loop, so every reported pacing number was computed against live state and the stale-`dps` load bug never touched them; the byte-identical timings before/after the loader fix corroborate this. OPEN FINDING for a NEW SESSION (not fixed; schema change needs sign-off): `GearInstance.dps`/`clickDamage` are STILL persisted and read directly by `getEffectiveStats` (state.ts:81-82) — `loadGame` patches them, it does not compute on read. Worse, the same derived-cache class affects two more fields the loader never normalizes: `player.baseAutoDps`/`baseClickDamage` (persisted copies of `BALANCE` constants, state.ts:32-33) and `combat.enemyMaxHp` (derived from stage, state.ts:38). Any future balance-formula change silently drifts those on existing saves. Structural fix = stop persisting derived values (store only source fields: itemLevel/upgradeLevel/definitionId, stage, and let base stats come from BALANCE) and compute on read; because that removes fields from the save blob it is a SCHEMA change → needs `CURRENT_SAVE_VERSION` bump + migration and therefore explicit user sign-off (brief stop condition). Highest-value pre-Expo refactor; "derived state drifts from source of truth" otherwise gets rediscovered in the RN codebase.
- 2026-09-26: Executed the drops-primary economy reversal as ONE delegated coder task carrying both the objective AND the root-cause diagnosis (gear stat was a power law in itemLevel while enemy HP is exponential in stage — a structural type mismatch no amount of number-nudging can fix). Result: 4 design iterations, pacing held (soft 6.39–6.52 min, hard 50.78–51.38 min, 5/5 seeds) AND drops became the primary lever. Contrast with the first build, where a planner's written estimate was wrong; here the acceptance criterion was MEASURED and multi-seed from the start, which is why it worked. Lesson: hand the subagent a falsifiable metric, not a prose goal.
- 2026-09-26: When a claim is backed by a metric the same agent authored, the independent reviewer must probe the METRIC, not just re-run the gates. Here the reviewer caught (a) the attribution ledger mislabeled gold GROSS as gold NET (charging equip reset-losses to drops), which paradoxically UNDERSTATED the objective — the true net drop share is ~100%, not 85.8%; and (b) that `loadGame` never re-derived `GearInstance.dps`, so a formula-derived cache silently went ~32× wrong on old saves after the balance change. Both fixes were small; neither was visible from the gates alone.
- 2026-09-26: Recurring hazard worth a standing rule — any persisted field that is a pure function of other persisted fields (here `dps`/`clickDamage` derived from itemLevel+upgradeLevel+formula) must be recomputed on load, because a balance change otherwise corrupts existing saves with a stale cache. We chose recompute-on-load over a version bump precisely because the SCHEMA did not change (only the formula), keeping `CURRENT_SAVE_VERSION` at 1 and the save-schema shape untouched.
- 2026-09-26: Honesty guardrails held under pressure: the brief's rule "if drops-primary breaks pacing, that IS the finding — don't re-neuter drops" was encoded as an explicit prompt instruction, and the outcome (drops primary at `dropChance=0.95`, real sensitivity at 0.8 where the soft sweep blows out to 2.24–8.40 min) is documented in `decisions.md` with "never widen the ±20% tolerance and never re-neuter drops; raise dropChance or add a pity counter" as the revisit trigger.
- 2026-09-25: Ran the full build as 6 delegated phases (scaffold → engine-core+tests → sim → web renderer → mobile smoke → docs) plus one economy redesign and one targeted fix round, on a greenfield repo. Model: opencode-go/deepseek-v4.1-flash, orchestrator with coder/designer/planner/reviewer subagents.
- 2026-09-25: The planner's economy numbers were the single highest-risk artifact and were genuinely wrong — it claimed a scratch sim hit ~6.2/~52.9 min, but the real sim produced a knife-edge exponential race (player ≈1.384×/stage vs HP 1.5×/stage) that passed on one seed and missed ±20% by 30–75% on four others. Lesson: for emergent/numeric designs, do not accept a written estimate; require the implementing agent to build a throwaway parameter-search harness and a MEASURED, multi-seed acceptance criterion before the design is treated as done.
- 2026-09-25: Making the seed sweep "informational WARNING" on a core acceptance metric let a fragile result look green (`PACING OK`, exit 0) while 4/5 seeds failed. Lesson: never downgrade a primary correctness signal to a warning — either make it a hard assertion or drop it. The redesign hardened it to an all-seed assertion, which is what surfaced the true state.
- 2026-09-25: Robustness was achieved by REMOVING variance (deterministic power core, drops power-neutral after a starter weapon), which hollowed out the brief's "gear drops → upgrade gear" lever. Lesson: when a fix makes a metric robust by making an input inert, surface that trade-off to the user explicitly rather than banking the green check — robustness-by-irrelevance is still a product decision.
- 2026-09-25: Ownership-based parallelism worked cleanly with zero file conflicts: engine-core (one coder, keeps interdependent interfaces coherent) → sim → web wiring (coder), then CSS polish (designer, sequential after DOM freeze) with the Playwright smoke test (coder) run in parallel because it owned disjoint files and depended only on already-frozen testids.
- 2026-09-25: Boundary claims in docs must be test-enforced. The README/decisions asserted "engine-core has no DOM lib" while `tsconfig.json` had no `lib`, so TypeScript default-injected DOM and `document.title` typechecked inside the engine. The reviewer's probe caught it; the fix added `"lib": ["ES2022"]` plus DOM/RN-global patterns to the fs boundary test. Lesson: every "the engine cannot do X" claim needs a failing-when-violated test, not prose.
