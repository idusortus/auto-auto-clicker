- 2026-09-28: Soft-lock fix shipped per the user's explicit direction: SURFACE the facts, never auto-rescue. The engine computes the advisory (`getSlotUpgradeAdvisory` / `getStallAdvisory`) using the SAME power metric the sim's equip policy uses (metric moved into `gear-stats.ts` as `powerScore`/`scoreWithEquip` and imported by the sim, so there is exactly one definition and the advisory can never recommend a downgrade). The renderer shows a `hint` badge whenever a strictly better bag item exists, escalating to a `nag` callout ONLY when the player is both stalled (no stage progress for 45s) AND holds a better item - with a button that dispatches the existing player `equip` action. Verified independently: in the reproduced defect it fires at stage 39 with ratio 2.71x, and a healthy progressing player never escalates past `hint`. Lesson: "fix the soft-lock" and "rescue the player" are different requirements - the user wanted the first; the second would have removed the decision that makes the game a game.
- 2026-09-28: Stall is detected WITHOUT persisting a new field, keeping the save schema at v4: the engine cannot reconstruct when the current stage began, so the HOST owns the anchor (in-memory `stageBeganAtMs` tracked across renders and passed via an optional render context). Honest limitation, documented: this measures time-on-current-stage, not a progress slope, so a player inching forward while holding a better item still gets a nudge past the window - acceptable because it only ever suggests, never acts. Lesson: when a feature's state is not in the save and adding it would bump the schema, look first for a host-owned derivation.
- 2026-09-28: Cost check on a "small" fix: the outdoor advisory work added a new leaf module, a shared metric, two getters, a render context, escalating UI, 12 unit tests and a smoke test - and grew `npm run smoke` from ~7s to ~24s (the new smoke test drives the Playwright clock to reach the stall window). Lesson for future sessions: guidance/UX features that depend on ELAPSED time are more expensive to test than they look, because the test must simulate the passage of time.
- 2026-09-28: ADVERSARIAL AUDIT found that the pacing proof was narrower than its green check implied. Wall timing is heavily POLICY-dependent: canonical greedy reaches soft 6.21/hard 50.25; a SMART equip-only player 6.25/45.5-52.0; upgrade-lazy 6.12/44.3-49.5; a passive clicker 4.26/28.2; and a NAIVE equip player (grabs the first bag item rather than the strongest) NEVER reaches either wall and stalls at stage 39 forever. So "soft ~6 min / hard ~54 min" is a property of one scripted playstyle, not a guarantee about the game. Corrected by ADDING a policy-sensitivity diagnostic section to `npm run sim` (informational, cannot gate the exit code) so the assumption is visible rather than hidden. Lesson: a green assertion proves the assertion, not the property you believe it stands for — ask what the harness is NOT varying.
- 2026-09-28: The audit also found a degenerate measurement: `getProjectedKillMs` projects `enemyMaxHp(stage)` against CURRENT sustained DPS, so for an UNARMED player (constant base DPS, no item-level lever) the projection collapses to a pure function of stage — the wall becomes unavoidable and identical regardless of gold/achievements/inventory. Documented in docblocks on `getProjectedKillMs`/`projectedKillMs`, surfaced via a new `isUnarmed(state)` getter (reported as `unarmed@end` in the sim), and pinned by a new test asserting the unarmed projection is stage-only and that equipping a weapon changes it.
- 2026-09-28: OPEN FINDING for a future session (not fixed): a naive player can SOFT-LOCK by equipping badly — verified stall at stage 39 for the full 120 min with a level-34 weapon equipped while a level-38 sat in the bag (bag of 24, gold 289). The game gives no signal that a better item is available or that the equipped one is worse, and the wall never fires because the projection is finite-but-slow rather than over threshold. Candidate fixes: an "upgrade available" nudge, auto-equip-best for idle players, or a bag/equipped comparison readout. None are trivial; worth a deliberate design pass rather than a patch, since it interacts with the drops-primary economy and the equip policy the sim models.

- 2026-09-27: The retune exposed a DESIGN CEILING worth remembering: per-slot allocation only bites while a slot has cap headroom. Rings/necklaces saturate their caps early (crit multiplier by item level ~4), past which a greedy policy correctly scores their next upgrade as exactly zero and skips it - so ~90% of gold still goes to the weapon. Genuinely diversifying would need higher caps, which would make gold a competing exponential and break the drops-primary gate. That is a deliberate ceiling, not a bug; recorded so it is not rediscovered as a surprise.

- 2026-09-27: The resolution (Option 3) came from asking what the wall is FOR. The wall is a designed gate on SUSTAINED power, so the fix was to separate sustained-vs-burst power: `sustainedActiveDps` excludes temporary boosts from the projection, while actual damage still gets them. That turned a knife-edge tuning problem into a bounded one — a burst of `D` ms at `M×` saves exactly `D×(M−1)` seconds regardless of stage or DPS, so rewards became predictable instead of fragile. Lesson: when a feature fights a constraint, look for the invariant the constraint is really protecting, then make the feature neutral to that invariant rather than trying to out-tune it.
