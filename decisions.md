## 2026-09-28 — Extract ALL user-facing text into a swappable `Theme` (build-time, output-identical)

**Context:** Groundwork for build-time swappable themes (text + colors + pixel art + animation). This phase ONLY extracts text and must be provably byte-identical: same strings, same DOM, same testids, same layout. The critical risk was conflating IDENTITY (achievement ids, gear `definitionId`s, `GearSlot`s, enemy ids, `ShinyKind`s, save schema) with DISPLAY (human copy) — identity is persisted in saves and asserted by the sim, so a theme must never be able to change it.

**Choice:** (1) A new leaf theme package at `engine-core/src/theme/`: `types.ts` defines a nested `Theme` contract (`ui`, `slots`, `enemy`, `shiny`, `advisory`, `achievements`), `fantasy.ts` holds the CURRENT wording VERBATIM (the "Standard Fantasy RPG" default), and `index.ts` resolves the active theme with a single `export const ACTIVE_THEME: Theme = fantasy;` — switching is that one line. `theme/types.ts` imports nothing (true leaf); `fantasy.ts` imports only the contract; no cycles. (2) Identity/display split: `achievements.ts` keeps each achievement's stable `id` and pure `unlocked` predicate in code (`AchievementSpec`), and resolves `title`/`description` at module load from `ACTIVE_THEME.achievements.catalog[id]` (keyed by id; a missing entry throws). The public `ACHIEVEMENTS: readonly {id,title,description,unlocked}[]` shape is unchanged, so `state.ts` (id validation) and `/web` are untouched at the call site. Interpolated descriptions (big-iron/hoarder/crit-maxed/loose-change/upgrade-veteran) are theme functions taking the balance value, so no balance number lives in the theme. (3) `/web/src/renderer.ts` imports `ACTIVE_THEME` from the engine package root and reads EVERY display string from it — including the SKELETON template literal (interpolated at module load), all aria-labels and `title` attributes, toasts, hints, empty states, slot/card/stat/bag formats, the advisory sentences, the offline summary, choice copy, and the milestone bonus wording (moved out of `state.ts`'s `describeMilestoneBonus`). `engine-core/src/index.ts` re-exports `ACTIVE_THEME` + `Theme`. (4) Interpolation stays in functions taking the same params (e.g. `enemy.bossCheckBody(stage, projected)`, `advisory.emptySlot(...)`), so output cannot shift.

**Trade-offs:** The theme surface is large (dedicated format-template slots such as `Lv ${level}`, `Cost ${cost}`, `DPS … · click … · upgrades …`, duration units) because the brief forbids ANY inline display string; this is deliberate. `ACTIVE_THEME` is resolved at module load, so a future RUNTIME theme picker would need a different seam (acceptable: this phase is build-time). Two host-shell/dev strings stay outside the theme — `web/index.html`'s `<title>` (static HTML, not renderer copy) and dev-only `console.error`/`throw` diagnostics — and are documented as remaining.

**Evidence:** `typecheck` 0 (3 workspaces); `test` 141/141 (12 files, unchanged); `sim` PACING OK, output **byte-identical** to pre-change (`diff` clean, canonical soft 6.21 / hard 50.25); `build` 0 (20 modules, was 18); `smoke` 17/17 unchanged. A throwaway deterministic Playwright harness (fake clock, fixed saves, fixed taps) dumped `#app` outerHTML+innerText across 12 scenarios (fresh taps/splash, full gear, revealed shelf, boss-check + wall choice overlays, offline summary, drop/frenzy claim + escape toast, stall advisory, milestone) — before vs after is **byte-identical**; the harness was removed. Module DFS: 33 files / 117 edges / **0 cycles**; `theme/types.ts` is an import-free leaf.

**Revisit:** When a runtime theme picker is wanted, replace the module-load `ACTIVE_THEME` const with a getter/context (and re-project on switch) — never move identity into the theme. If the theme grows non-text fields (colors/art/animation), keep them in the same nested object and keep `types.ts` a leaf.

## 2026-09-28 — Plumb the engine's `GameEvent[]` through to the web renderer (animation seam, no-op)

**Context:** `/web` received only a state DIFF, so the renderer could not tell "the enemy was just hit" or "the enemy just died" from "a number got smaller". A future themeable animation system needs real event triggers. The engine already emits a correct `GameEvent[]` from `advance`/`applyAction`; the host discarded it. This phase must be a provable visual NO-OP (no new animation/UI) so the plumbing is verifiable in isolation.

**Choice:** (1) **`render(state, context?, events?)` — events as an additive third parameter, not a separate `pushEvents` method.** A `GameEvent[]` and the `GameState` it produced are the two outputs of the same simulation step(s), so delivering them in one call keeps them atomic, preserves order, and needs no pending buffer: events are consumed and discarded inside the call, so memory is bounded by one frame. A separate `pushEvents` would add a buffer plus a call-order hazard (push before vs after `render`) for no benefit. (2) **Per-frame coalescing.** The rAF `frame()` loop runs several 100 ms `advance` steps; it concatenates every step's `.events` into one ordered `frameEvents` batch and renders once with it, so each event is delivered exactly once, in order, one batch per frame. `dispatch` forwards `applyAction(...).events`. (3) **Offline + boot events are DELIBERATELY DROPPED.** `replayOffline` (up to 8 h at 1000 ms steps) would otherwise emit thousands of events and trigger an animation storm for history the player never watched; only the resulting state is delivered (the existing state-diff behaviours still cover it), and the boot render carries no events. (4) **`handleEvents(events)` is the documented private seam** — a single function with a `TODO(animation)` describing the future event→trigger mapping; it is a deliberate no-op this phase so the projection is byte-identical. (5) The existing non-blocking flourishes (achievement splash, Shiny toast/flourish, milestone flourish, advisory) keep their state-diff triggers unchanged; only their now-stale "the host passes no events" comments were updated.

**Trade-offs:** The renderer now has two parallel inputs (state diff + event batch) and existing cues migrate to events only in a later phase, so there is temporary redundancy. `render`'s third parameter is optional and positional (an options object would be churn). Offline progress intentionally produces no animations even though it produced real kills/levels.

**Revisit:** If a theme wants an *offline* summary animation, add an explicit bounded/summarised offline-event path — never a raw replay of every offline event. If more optional params accrete, switch `render` to an options object.

**Evidence:** `typecheck` 0; `test` 141/141; `sim` PACING OK (canonical soft 6.21 / hard 50.25, all-seed hard 45.01–46.80 — engine untouched); `build` 0; `smoke` 17/17 unchanged. Temporary `handleEvents` instrumentation (removed after the run) recorded **51 events delivered across 40 taps**, in order — `damageDealt`, `achievementUnlocked`, `goldChanged`, `enemyKilled`, `stageEntered` — proving real delivery.

## 2026-09-28 — Presentation-only UI: strongest-first bag sort + achievements hidden-by-default toggle

**Context:** Two small /web UX changes, no engine change. (1) The bag rendered in raw `state.gear.bag` array order, so the strongest drop was not necessarily on top and the shelf could disagree visually with the advisory/sim ranking. (2) The achievements shelf rendered all ~30 entries, so a fresh player saw a tall list of `???` / `Locked` with no way to focus on what they had actually earned.

**Choice:** (1) **Bag sorted strongest-first by the engine's own metric.** `sortedBag(state)` ranks each item by `scoreWithEquip(state, gearDefinitionFor(item.definitionId).slot, item)` — the SAME shared power metric (`gear-stats.ts`) the upgrade advisory and the sim's economy policy use — so /web duplicates no balance math and the order can never disagree with guidance. Deterministic tie-break: item level desc, then instance id. The render-diff `lastBagSignature` is computed from the **sorted** array and includes `definitionId`, so any change in the *displayed order* changes the signature and forces a re-render (raw-array-order changes alone would not). (2) **Achievements hidden by default with a toggle.** Locked catalog entries stay in the DOM (so the existing `achievement-item` count and the `N unlocked` count stay honest) but are marked `hidden`; a real `achievements-toggle` button in the section header flips a renderer-local `revealLockedAchievements` flag and re-projects, rendering locked entries as the existing `???` / `Locked` tease. The toggle exposes `aria-expanded`/`aria-controls`, is ≥44px (`.btn--small`), reads `Show hidden N` / `Hide hidden`, and is hidden when nothing is locked. The renderer's local flag is never persisted and the toggle never dispatches an engine action; `lastAchievementsSignature` includes the reveal flag so a flip re-renders. The `achievements-count` element keeps its number (smoke-test contract) and a sibling renders ` of TOTAL unlocked`; an all-locked shelf shows an empty-state hint.

**Trade-offs:** (a) Locked entries are present-but-`hidden` rather than absent, which keeps the existing `achievement-item` count assertion green while the shelf visually shows only unlocked entries; a reviewer reading the DOM sees the full catalog. (b) Re-projecting on toggle calls the whole `render`, but every other channel is diff-guarded (achievement splashes, milestone/shiny diffs) so no spurious splash/flourish fires. (c) The toggle is renderer-local, so it resets on reload — deliberate (presentation state, not a persisted preference).

**Revisit:** If the shelf must not keep locked entries in the DOM at all, move to render-only-visible and update the smoke assertion accordingly — still no engine change. If bag ordering should weight a different metric, change it in the engine's `powerScore`, never by duplicating math in /web.

## 2026-09-28 — Soft-lock fix: surface a better bag item, let the PLAYER decide (never auto-equip)

**Context:** A player who equips badly (grabs the first bag item rather than the strongest) can stall forever: the stage projection stays finite-but-slow so neither the boss check nor the progression wall ever fires. Measured on seed 12345: stalled at stage 39 for the whole 120-min run with a level-34 weapon (dps 7456) equipped while a level-38 weapon (dps 20203) sat in the bag (2.7× power gap). The user's instruction: *"make the user have to decide, with guidance … if the player is too dumb to realize they have a better weapon in the bag they're not really playing the game."* Hard constraints: no automatic equipping / rescue / forced state change of any kind; no balance number, `BOSS_TIMER_MS`, `HARD_WALL_PROJECTED_KILL_MS`, ±20 % tolerance, canonical range, drops-primary gate, or existing assertion changed; save schema stays **v4** and `DEFAULT_SAVE_KEY` unchanged; engine-core stays pure (no clocks/`Math.random`); `/web` holds no balance numbers.

**Choice:** (1) **One shared power metric, moved into the engine.** `powerScore(state)` + `scoreWithEquip(state, slot, item)` now live in the leaf `gear-stats.ts` (`powerScore = sustainedActiveDps(state) × (1 + goldMultiplier)`), and the sim imports them — its local copies are deleted. Because the sim's economy policy and the new advisory rank candidates with the identical function, the advisory can never recommend a downgrade relative to the policy. The metric deliberately excludes the temporary frenzy boost (a uniform positive factor on every comparison, so it cannot change any ranking); **proof of no behaviour change: the canonical sim sections are byte-identical to pre-move (`diff` clean, soft 6.21 / hard 50.25).** (2) **New leaf `advisory.ts`** with `getSlotUpgradeAdvisory(state, slot)` → `{ slot, hasUpgrade, currentPower, bestPower, ratio, bestInstanceId }` and `getStallAdvisory(state, stageBeganAtMs?)` → `{ severity: 'none'|'hint'|'nag', stalled, stalledMs, stage, best, upgrades }`. Both getters are pure reads; **no new `GameEvent`** (the renderer deliberately receives no event list, so it diffs state instead — an event would add surface for nothing). (3) **Stall detection adds no persisted state.** The engine cannot reconstruct the current stage's start time from `GameState`, so the HOST owns the anchor: `main.ts` watches `combat.stage` across renders and keeps `meta.totalPlayedMs` in memory, passing it into the new optional `render(state, { stageBeganAtMs })` context. No persisted field, no schema bump (v4), `DEFAULT_SAVE_KEY` untouched. Without a finite anchor, `stalledMs = 0` → `none`. (4) **Both conditions required**: a non-`none` severity needs a stall window (`STALL_HINT_MS` 15 s → `hint`, `STALL_NAG_MS` 45 s → `nag`; new guidance-only constants in `balance.ts`, never read by the sim) AND a strictly better bag item, so a legitimately-walled player is never nagged. (5) **/web surfaces, never decides.** A modest per-card badge (`upgrade-advisory-badge`) and a `bag-upgrade-tag` on the flagged item appear for any available upgrade; at `nag` a prominent inline callout (`upgrade-advisory`) states the facts — stage, duration, the `Level N` item, and the engine's `~X×` ratio — with one button (`upgrade-advisory-equip`) that dispatches the EXISTING `{ type: 'equip', instanceId }`. Inline (not an overlay), no new motion, so it cannot block the tick loop or collide with the splash/Shiny messages, and reduced-motion is a no-op. The callout is a pure projection; the equipped item changes ONLY on the player's tap.

**Evidence (all gates re-run):** `npm run typecheck` 0; `npm run test` **129 → 141 passed (12 files)** — new `advisory.test.ts` (12 tests: strictly-better upgrade, no-upgrade when the bag is weaker/equal, never-a-downgrade once the best is equipped, rings + necklace handled through the shared metric, empty-slot upgrade, `scoreWithEquip` ≡ equipped-state `powerScore`, `getStallAdvisory` returns `none` while progressing or with no upgrade, `hint`→`nag` escalation at the thresholds, no persistent field / schema v4); `npm run sim` **PACING OK (exit 0)** with canonical sections **byte-identical** to pre-change (`diff` clean; canonical soft 6.21 / hard 50.25, all-seed hard 45.01–46.80, drops-primary net 97.4–98.6 %); `npm run build` 0; `npm run smoke` **13 → 14 passed** (the new test drives the advisory condition with the Playwright clock, asserts the callout states the facts — stage 39, "no progress", `Level 38 weapon`, `Level 34` — and that tapping its button equips the item). Module graph: `advisory → gear-stats/balance/content/types` is acyclic; `gear-stats` stays a leaf.

**Trade-offs / deviations:** (a) `getStallAdvisory` takes an OPTIONAL second argument (`stageBeganAtMs`) rather than reading a persisted anchor — the only way to keep schema v4 and the engine pure. Without it the severity is `none`. (b) The stall window measures time on the **current stage**, not a slope: a player genuinely inching forward while a better bag item sits unused will still be prompted after the window. That is deliberate (it is exactly the finite-but-unusably-slow soft-lock shape) and the prompt only ever SUGGESTS. (c) `scoreWithEquip` keeps an explicit `slot` parameter (the brief sketched `(state, item)`); the slot form is what the sim already used and avoids an extra content lookup. (d) No `advisoryRaised` `GameEvent` was added (optional in the brief): the renderer receives no event list, so an event would not simplify anything.

**Revisit:** If the renderer is ever given the event list, an advisory-threshold event could replace the state diffing. If non-weapon slots must be treated differently in the copy, extend `advisory.ts` — never duplicate the power metric in `/web` and never make the game equip on the player's behalf.

## 2026-09-28 — Audit corrections: sim policy-sensitivity diagnostic + documented unarmed projection degeneracy

**Context:** An adversarial audit found two honesty gaps in the pacing proof. (1) The green `npm run sim` check measured ONE scripted policy (greedy) and its framing implied a property of the game; wall timing is demonstrably policy-dependent. (2) For an unarmed player, sustained DPS is a constant, so `getProjectedKillMs` degenerates to a pure function of the stage — the wall is unavoidable and identical regardless of player action — and that accident was neither documented nor visible in the sim output. Hard constraints: change NO balance number, threshold, ±20% tolerance, canonical range, or existing assertion; save schema stays v4; `DEFAULT_SAVE_KEY` unchanged; engine-core stays pure.

**Choice:** (1) **Additive policy sensitivity.** `runSim` now takes an `EconomyPolicy` (`greedy` default, plus `passive` / `equip-only` / `upgrade-lazy`); clicking, choice resolution (`wait`), and Shiny claiming stay identical across policies so a timing difference is attributable to the economy policy alone. The `greedy` path and every hard assertion are unchanged (verified: the canonical sim sections are byte-identical to pre-change, `diff` clean). `main()` prints a clearly-labelled `policy sensitivity (DIAGNOSTIC — informational only; does NOT gate the exit code)` section reporting soft/hard time+stage per seed and an `unarmed@end` flag; it never touches `failed`/`process.exitCode`. (2) **Degeneracy documented and surfaced.** Precise docblocks on `getProjectedKillMs` (`state.ts`) and `projectedKillMs` (`balance.ts`) state that the projection depends on CURRENT sustained DPS; that the weapon is the only item-level power lever, so with no weapon equipped DPS cannot grow; and that for a gear-less player the projection is a pure function of `combat.stage` — which is why wall timing is policy-dependent. A cheap leaf getter `isUnarmed(state)` (true when no weapon is equipped) is added in `gear-stats.ts`, re-exported through `state.ts`/`index.ts`, and used by the sim's `unarmed@end`. (3) A new `engine-core/tests/projection.test.ts` pins the documented property.

**Evidence (measured; all gates re-run):** canonical sim sections byte-identical (`diff` clean); `npm run sim` → PACING OK (exit 0), canonical soft 6.21 / hard 50.25, all-seed hard 45.01–50.25. Diagnostic rows across the 5 sweep seeds: greedy soft 5.76–6.21 (st30) / hard 45.01–50.25 (st50); **equip-only** soft 5.79–6.27 (st30) / hard 45.46–51.98 (st50), `unarmed@end=no`; **upgrade-lazy** soft 5.67–6.13 (st30) / hard 44.28–49.47 (st50); **passive** soft 4.07–4.45 (st10) / hard 28.18–28.94 (st15), `unarmed@end=yes` — the passive row is the degenerate pure-stage case (stage 15, not a boss, walls purely on the enemy curve). `npm run test` 126 → **129 passed (11 files)**; `typecheck` 0; `build` 0; `smoke` 13/13; `npm run sim` terminates in ~22 s (bounded by the existing caps plus `MAX_POLICY_ECONOMY_PASSES = 1000` and `MAX_SIM_STEPS`).

**Trade-offs / deviations:** (a) The audit's probe numbers (passive ~13.3 min, equip-only reaching neither wall) differ from the values measured here; this implementation follows the brief literally — `passive` includes the active player's 2 clicks/sec, and `equip-only` equips the best bag item every tick. Under those definitions equip-only tracks the stage and reaches the same stage-50 wall as greedy (consistent with gold being a *minor* lever), while passive walls at stage 15. (b) The diagnostic adds ~18 s to `npm run sim` (fifteen extra runs). (c) The alternative policies still claim Shinies and resolve choices, exactly as the canonical fixed loop does, so only the economy step varies by design. No save field, balance number, threshold, tolerance, canonical range, or existing assertion changed; `/web` is untouched and still holds no balance numbers.

**Revisit:** If CI cost matters, trim the diagnostic seed set or gate it behind a flag — never remove the canonical assertions or let a diagnostic row gate the exit code.

## 2026-09-27 — Option A gold retune: flatten the upgrade cost curve so milestones actually fire (gold stays minor)

**Context:** The measured diagnosis was that gold was *functionally absent*, not a minor lever. Flat gold income is ~305 kill-gold for a whole 50-stage run while the upgrade curve was `base 10 / growth 6 / stat 1.05` (cumulative cost 10, 70, 430 …), so a run afforded ~2 levels ≈ +10 % power against a ×1.42/stage enemy curve. Worse, the weapon is replaced by a same/lower-stage drop almost every kill (drop `itemLevel` tracks the stage; `gearGrowth 1.283` >> `upgradeStatMultiplier 1.05`, so one extra item level beats ~5 upgrade levels), which resets `upgradeLevel` to 0 — so item levels peaked at 2–7 and the every-3-levels **milestone** channel was dead content (0–2 milestone events per run). The brief: keep gold a MINOR lever but make the curve LEGIBLE, get a single item to ~8–12 levels so milestones genuinely fire and repeat, and give per-slot allocation a real reason to exist — WITHOUT touching `BOSS_TIMER_MS`, `HARD_WALL_PROJECTED_KILL_MS`, the ±20 % tolerance, the canonical comfortable ranges, or the drops-primary gate.

**Choice:** Flatten the curve and shrink the per-level step, one lever at a time (throwaway sweep harness in `/tmp/opencode`, ~5 rounds + refinements, all 5 seeds): `upgradeCostBase` **10 → 3**, `upgradeCostGrowth` **6 → 1.25**, `upgradeStatMultiplier` **1.05 → 1.01**. `goldGrowth` stays 1.0 (flat income kept). No other constant changed; the milestone interval stays 3 and the caps stay as-is.

**Why the stat multiplier had to move too (the key finding, contradicting the starting suggestion):** the suggested direction (growth 1.35–1.5, base 8–10, `stat 1.05`) was validated and FAILS to reach the goal — it tops out at ~14 milestones per run before the pacing gates break. With `stat = 1.05`, any curve cheap enough to afford 8+ levels lets the weapon reach `1.05^L > 1.283` (L ≈ 6), at which point the current weapon is BETTER than the next drop, so the player stops swapping, gold power compounds, and the canonical hard wall falls below its 48.0 min comfortable floor (measured: base 3 / growth 1.4 / stat 1.05 → canonical hard 47.19 → FAIL). Dropping the per-level step to **1.01** means a +1 item-level drop (×1.283) beats ANY affordable upgrade stack (it takes ~25 levels at 1.01 to match one item level), so the weapon keeps tracking the stage, most upgrade power is reset by each equip, and gold stays the smoothing lever. The visible step is the milestone, not the per-level nudge.

**Evidence (5 sweep seeds; every gate green; no threshold/tolerance/canonical range/assertion changed):**
- **Milestones genuinely fire now: 17–23 per run** (was 0–2), per-slot `w16–19 / r0–4 / n0–2`; **per-item peak level 8–12** (was 2–7). Canonical seed: 21 milestones (w18/r3/n0), max level w8/r9.
- Pacing: canonical soft **6.21** / hard **50.25** (both inside comfortable [5.2,6.8]/[48,60]); all-seed soft 5.76–6.21, hard **45.01–46.80** (all inside [4.8,7.2]/[43.2,64.8]); zero-gold reference hard was 45.46–51.98, so gold's real wall-clock effect is ~2–3 %.
- Drops-primary net **97.4–98.6 %** (was 98.3–99.6 %; a measured, acceptable decline as gold gets more real — drops remain the large majority). Gross share 91.0–91.4 %. `goldNet` +0.169…+0.318.
- Per-slot split: w86–101 / r0–13 / n0–7. The weapon still dominates — see the honest finding below.
- Free path: `wait`/`watchAd` still grant exactly 2 / 4 upgrade LEVELS (`WAIT_UPGRADE_GRANT_LEVELS` / `WATCH_AD_UPGRADE_GRANT_LEVELS` unchanged), so their power value is unchanged; their gold-denominated share fell to **0.4 %** (from 4.5–13.5 %) purely because two levels now cost less gold. Pacing is unaffected.
- Sim output extended to report per-slot milestone counts and per-slot peak upgrade level (engine getters only, no balance math duplicated). Schema stays **v4** (balance-only change; nothing persisted changed). Engine tests unchanged 126/126; smoke 13/13; typecheck/build 0.

**Honest finding — the weapon still absorbs most upgrades, and that is genuine, not a policy bug:** the weapon is the only *unbounded* lever and its next level is always cheap (it resets to 0 every equip), so its absolute `powerScore` gain beats a ring/necklace almost every tick. Rings/necklaces saturate their caps early (crit multiplier by item level ~4, single-ring crit chance by ~15), so an upgrade there frequently scores exactly **zero** gain and the sim's (correct) policy skips it. Seeds whose only ring drops after it has cap headroom show zero ring upgrades (diagnosed: seed 999/424242 *did* equip a ring but its crit contribution was already cap-saturated). Seeds that get an early ring with headroom DO invest (max ring level up to 12, r4 milestones). The sim policy was therefore left unchanged — it already spends only where real power improves (engine getters only); the concentration reflects the designed caps, not shape-following.

**Trade-offs / deviations:** (1) `upgradeStatMultiplier` moved even though the starting suggestion only named the cost curve — it is *required* for the milestone goal to coexist with green pacing, and it strengthens (not weakens) drops-primary. (2) The per-slot allocation "bites" only while a slot has cap headroom; past the caps gold on non-weapon slots is genuinely dead, which is the pre-existing deliberate ceiling, not fixed here (raising caps would make gold a competing exponential and break the drops-primary gate). (3) `upgradeCostGrowth 1.25` sits below the suggested 1.35–1.5 band because base 3 + stat 1.01 already affords the target levels at a lower, more legible total power.
**Revisit:** If non-weapon slots must stay meaningful late, give milestones/upgrades a new non-multiplicative channel or raise the caps *together with* a re-proof of the drops-primary gate — never by re-steepening the cost curve (that re-kills milestones) or widening tolerance.

**Context:** `/web` had a single "Upgrade weapon" button (the renderer hard-coded `slot: 'weapon'`) even though `applyUpgrade`/`getUpgradeCost` were already slot-generic, so gold was a mandatory single tap rather than a choice. The brief: one upgrade control per equipped slot; a VISIBLE every-Nth-level step bonus that stays a *minor* lever (no new effect types, no cap bypasses); and a sim economy policy that stays honest with four upgrade targets in play.
**Choice:** (1) **Per-slot upgrade controls.** `/web` renders four rows (`upgrade-btn` for the weapon — the original testid, kept for the smoke test — plus `upgrade-btn-ring1`/`upgrade-btn-ring2`/`upgrade-btn-necklace`), each with its own `upgrade-cost`/`upgrade-level` readout, independently disabled when the slot is empty or the cost exceeds gold, dispatching `{ type: 'upgradeEquipped', slot }`. `RendererHandlers.onUpgrade` is now slot-aware. (2) **Derived milestones.** `UPGRADE_MILESTONE_INTERVAL = 3`; `UPGRADE_MILESTONE_BONUS` maps each slot to a small bonus on the EXISTING capped stats (weapon → power, rings → crit chance+crit dmg, necklace → gold). The bonus is a pure function of the item's `upgradeLevel`, folded into the SAME clamped aggregations (`getCritStats`/`getGlobalBonuses`), so no new save field exists and the schema stays **v4**. New pure getters `getMilestoneInfo(slot, upgradeLevel)` and `getSlotMilestones(state)` return `{ slot, interval, achievedCount, nextAtLevel, bonusDescription }`, with the wording built from the balance numbers so `/web` holds none. (3) **Visible step change.** `applyUpgrade` emits a new `milestoneReached` GameEvent on a crossing; `/web` diffs each slot's `achievedCount` across renders (the renderer still receives no event list — same technique as the achievement shelf), shows a brief non-blocking flourish above the Shiny messages, and renders a `★ ×N — …` badge on the affected card. (4) **Sim policy.** `runEconomy` now buys the affordable upgrade — across all four slots — with the largest `powerScore` gain (engine getters only), and never buys a zero-gain upgrade, so it cannot dump gold into a capped dead lever. Per-slot upgrade counts and milestone crossings are reported. (5) Three snarky achievements (`milestone-first`, `upgrade-diversified`, `upgrade-veteran`); catalog 27 → 30, test bound 18–30 → 18–33.
**Why the necklace milestone is gold-only (measured):** a necklace's raw power base (0.05) already exceeds `POWER_MULTIPLIER_CAP` (0.02), so a power milestone there would be dead on arrival (a badge advertising a gain that the cap erases). Gold keeps headroom until the necklace's own gold bonus saturates its cap.

Total crit chance is capped at `CRIT_CHANCE_CAP = 0.75`. `critMultiplier` is a *contribution* to the crit-damage bonus (`total = 1 + sum`), so a 0 contribution cannot turn a crit into a penalty. New getters `getCritStats(state)` and `getGlobalBonuses(state)` expose the parts; `getGoldReward(state, stage)` and `getChoiceGoldGrant(...)` are the single places the gold bonus is applied (kill + free-path grant). Two ring definitions (`ring1`/`ring2`) share one `RING_BASE` and are slot-bound so `definitionId → slot` routing stays a pure lookup.
**Trade-offs:** All four effects use placeholder magnitudes (Phase 2 owns tuning); the exponential scaling on a *multiplicative* bonus means ring/necklace power grows very fast at high item level, and the sim currently fails the ±20% windows as a result. Effective stats are now fractional; integer damage is preserved only by flooring at the `advance`/`click` damage-application boundary. Dropped gear is no longer always a weapon, so the weapon stream is thinner (weights: weapon 1.0, ring1/ring2 0.25, necklace 0.02) and a guaranteed-first-weapon override applies until a weapon is owned.
**Revisit:** Phase 2 retunes the ring/necklace factors and drop weights against the sim; if the multiplicative growth proves structural, cap the multiplier contributions or change their scaling helper (never widen the ±20% tolerance).
**Status:** Phase 2 (below) restored pacing by retuning `SLOT_DROP_WEIGHTS` only; the ring/necklace **factors were left unchanged** because the sim never equips non-weapons, so they are sim-inert. The structural exponential-scaling risk for real players stands.

## 2026-09-26 — Save schema v2: persist source fields only, derive everything on read
**Context:** Three field groups in `GameState` were pure functions of other fields or of `BALANCE`, yet were persisted: `GearInstance.dps`/`clickDamage` (from `computeGearStats(definitionId, itemLevel, upgradeLevel)`), `GameState.player.baseAutoDps`/`baseClickDamage` (copies of `BALANCE.baseAutoDps`/`baseClickDamage`), and `GameState.combat.enemyMaxHp` (from `enemyMaxHp(combat.stage)`). The user approved the structural fix.
**Choice:** `CURRENT_SAVE_VERSION` is now 2 and `GameState` persists SOURCE fields only: `player.gold`, `combat.{stage,enemyHp,damageCarry}`, gear instances as `{id,definitionId,itemLevel,upgradeLevel}`, plus `meta`/`choices` bookkeeping. Migration is one-way (a migrated save reloads as v2), and the localStorage key stays `auto-auto-clicker.save.v1` so old saves are still found and migrated — a future key rename must keep the migration path. Deriving on every read costs a `Math.pow`/`floor` per getter call (negligible here; the renderer already caches by signature), and the state is no longer a literal snapshot of what the host displayed.
**Revisit:** If a derived value ever becomes genuinely expensive or needs a cheap reverse lookup, add a non-persisted memo with an explicit invalidation rule — never re-persist it. If the schema changes again, add `migrateV2ToV3` alongside `migrateV1ToV2`.

## 2026-09-26 — Economy reversal: drops are the primary power lever, gold demoted
**Context:** The Phase 3b "deterministic power core" made gear drops power-neutral after the guaranteed starter weapon so every sweep seed produced identical timings. The user reversed that decision directly: gear DROPS must be the primary driver of power growth, with gold-funded upgrades demoted to a minor smoothing lever. The old design could not satisfy it structurally — gear stat was a power law in item level (`dpsFactor * itemLevel^levelExponent`) while enemy HP is exponential (`hpGrowth^stage`), and drops trailed the stage by `DROP_LEVEL_OFFSET = 6` at `dropChance = 0.08`, so a polynomial lever could never drive an exponential curve.
**Choice:** Gear stats are now EXPONENTIAL in item level (`floor(factor * gearGrowth^(itemLevel - 1))`, same for click damage) with `gearGrowth = 1.283`; `GearDefinition.levelExponent` is replaced by `gearGrowth` (content, not save state). `dropChance` is 0.95 and `DROP_LEVEL_OFFSET` is 0, so a killed stage reliably yields a weapon whose item level tracks that stage (`itemLevel = max(1, stage)`) — a modest integer in lockstep with the stage. Gold is a minor lever: `upgradeStatMultiplier = 1.05`, `upgradeCostGrowth = 6`, flat gold (`goldGrowth = 1.0`), so only ≈0.7 upgrade levels are affordable per equip, and equipping a new drop resets `upgradeLevel` to 0 — cheap relative to the ≈28% item-level jump. `hpGrowth` is 1.42 so player power (≈1.28×/stage) falls behind enemy HP (1.42×/stage) at the designed ratio; the stage-30 boss is the soft check and the stage-50 boss the hard wall. The sim now carries a power-attribution ledger: the equipped stat's log decomposes exactly into per-equip `Δ(itemLevel − 1)·ln(gearGrowth)` plus per-upgrade `+ln(upgradeStatMultiplier)`, computed only from exported engine values (`BALANCE`). The reset loss from each equip is charged to gold (`goldNet = goldGross − resetLoss`), never subtracted from drops, so gold's net contribution is ≈0 and drops carry ≈100% of net log-power growth. A drops-primary gate — drops must exceed 50% of positive *net* log-power growth — is a hard per-seed assertion alongside the unchanged ±20% pacing windows, plus a drop-stream sanity guard (equips must keep pace with stages cleared).
**Trade-offs:** Drop RNG now influences pacing, so the 5-seed sweep is a real robustness probe instead of a determinism guard; `dropChance` 0.95 keeps the spread tight (soft 6.39–6.52 min, hard 50.78–51.38 min, drops ≈100% net / 87.6% gross of log growth; `goldGross = resetLoss = 1.659`, so `goldNet = 0`), but a dry spell can still shift a crossing — at `dropChance` 0.8 the observed soft range blows out to 2.33–8.75 min. Determinism and seed-robustness are the explicit price of a drops-primary economy. `goldGrowth = 1.0` makes late-game gold flat and, with steep costs, gold is a small lever (≈0% of NET log growth — the upgrade power it buys is destroyed by the resets; 12.4% gross; the free `wait` grant ≈4.5%). The `/web` smoke test's "keep upgrading until DPS rises" assertion encoded the old economy and was repointed at equipping a higher-level drop; `/web/src` is unchanged and still holds no balance numbers.
**Revisit:** If drop-RNG pacing variance becomes unacceptable, raise `dropChance` toward 1.0 (or add a per-stage pity counter) — never widen the ±20% tolerance and never re-neuter drops. If gold should be a larger lever again, that is a new design decision, not a tuning tweak.

## 2026-09-25 — Determinism and numeric precision
**Context:** Headless sim must be reproducible and offline progress must not drift.  
**Choice:** All combat/economy numbers are integers. Auto-damage is calculated as `floor((dps * deltaMs + carry) / 1000)` with a per-state damage carry that is a fraction in `[0, 1)`. RNG is a seeded mulberry32 whose state is stored in `GameState.meta.rngState`.  
**Trade-offs:** Formulas use `Math.pow` then `Math.floor`; results could differ by 1 across JS engines near integer boundaries, mitigated by floor and conservative tolerances.  
**Revisit:** If porting to a host with a very different JS engine (e.g., old Hermes), re-test integer boundaries.

## 2026-09-25 — Pacing thresholds and economy baseline
**Context:** Pacing must be provable by headless sim, not manual play.  
**Choice:** Soft boss check = first `BossCheckFailed` event (projected boss kill > 60 s). Hard progression wall = first `ProgressionWall` event (projected kill > 600 s). Baseline balance constants are defined in `/engine-core/src/balance.ts` (e.g., `hpGrowth = 1.5`, `weaponLevelExp = 1.4`, `upgradeStatMultiplier = 1.18`).  
**Trade-offs:** Targets are sensitive to these constants; sim will validate and expose tuning knobs.  
**Revisit:** After sim results; only constants change, not the schema or API.
**Superseded by:** "Deterministic power core: bounded RNG, bounded free grants, DPS-based swap" (Phase 3b) — the baseline constants changed; only the schema/API claim still holds.

## 2026-09-25 — Web renderer stack
**Context:** Renderer is disposable; the permanent artifact is engine-core.  
**Choice:** Web uses Vite + TypeScript + vanilla DOM. It holds zero balance numbers, drop tables, or state mutation; it only calls `engine-core` functions and renders returned state/events.  
**Trade-offs:** No component framework means slightly more manual DOM, but zero framework dependency and a thin boundary.  
**Revisit:** If the Expo port wants to reuse web code, migrate to a framework; not needed now.

## 2026-09-25 — All tuning constants live in `balance.ts`, re-exported by `index.ts`
**Context:** The public constants (`BOSS_TIMER_MS`, `HARD_WALL_PROJECTED_KILL_MS`, `ACTIVE_CLICKS_PER_SECOND`, `CURRENT_SAVE_VERSION`, `BAG_CAP`) are read by engine and host code that also imports the economy formulas. Defining them in `index.ts` would create import cycles (`advance` → `index` → `advance`).
**Choice:** Define every constant and formula in `src/balance.ts`, then re-export the constants from `src/index.ts`. Consumers see the exact same names and values; there is still exactly one file to tune.
**Trade-offs:** `index.ts` contains re-exports rather than literal `const` declarations, so a reader must follow the re-export to find a value.
**Revisit:** Never; adding a second tuner file would defeat the single-knob design.

## 2026-09-25 — Tick/choice edge semantics for `advance` and `resolveChoice`
**Context:** The brief specifies multi-enemy ticks and three choice outcomes but leaves ordering ambiguous.
**Choice:** In one tick, integer auto-damage is consumed sequentially across enemies (kill, spawn next, continue with the remainder); leftover damage is discarded when a pending choice blocks progression. `resolveChoice('iap')` clears the original pending choice, then performs a real kill whose own stage-entry checks may raise a fresh pending choice for the next stage; `'wait'`/`'watchAd'` only grant gold and never re-run stage-entry checks in the same call.
**Trade-offs:** A single enormous `deltaMs` can traverse many stages and emit many events; overkill past the final kill in a tick is lost rather than banked.
**Revisit:** Only if the sim shows banking overkill is needed for pacing accuracy.

## 2026-09-25 — Async `SaveRepository` + structural localStorage adapter
**Context:** Saves start local but must later move to Supabase; engine-core's tsconfig has no DOM lib.
**Choice:** `SaveRepository` is `Promise`-based (`load(): Promise<SaveGame | null>`, `save(): Promise<void>`). `LocalStorageSaveRepository` declares a minimal structural `StorageLike` interface and reads `(globalThis as { localStorage?: StorageLike }).localStorage`; when absent, `load()` resolves null and `save()` rejects with a clear error. `saveGame`/`loadGame` (with version check) live in `src/state.ts`. `@types/node` is an engine-core devDependency, used only by the fs-based boundary test.
**Trade-offs:** No `clear()` method yet (not required this phase); the async surface costs an `await` even for localStorage.
**Revisit:** When the Supabase adapter lands, revisit whether `clear()` and conflict/version metadata belong on the interface.

## 2026-09-25 — Headless pacing simulator (Phase 3)
**Context:** The pacing target must be proven by an automated harness, not manual play. Phase 3 needed a deterministic, wall-clock-free driver of the pure engine.
**Choice:** `sim/src/sim.ts` advances a virtual clock in fixed 100 ms steps up to 2 h, clicks every 500 ms (`1000 / ACTIVE_CLICKS_PER_SECOND`), resolves any pending choice on the free `wait` path, and runs a greedy economy after each tick (upgrade the equipped weapon while affordable, then equip the best strictly-higher-`itemLevel` bag weapon). It records the first `bossCheckFailed` and first `progressionWall` from the tick that sets `choices.pending`. Canonical seed `12345` is the hard assertion (soft 6.0 min ±20%, hard 54.0 min ±20%); four extra seeds are informational warnings only. Exit code 1 on canonical failure, 0 on pass.
**Trade-offs:** The sim must mirror a real player's policy, so it cannot assume perfect play; the greedy itemLevel swap forfeits upgrade levels, which makes outcomes highly sensitive to drop RNG.
**Revisit:** If sweep-seed robustness becomes a requirement, revisit the sim's swap policy (itemLevel vs stat comparison), never the tolerance.
**Superseded by:** "Deterministic power core: bounded RNG, bounded free grants, DPS-based swap" (Phase 3b) — the swap policy is now DPS-based and all seeds are hard assertions.

## 2026-09-25 — Pacing tuned via economy levers (Phase 3)
**Context:** The canonical seed initially produced soft 3.92 min and hard 10.39 min — both far short of 6.0/54.0 min. Tuning had to stay inside `balance.ts` and keep every engine test green, including behavioral pacing scenarios.
**Choice:** Two committed lever changes: `gear.upgradeStatMultiplier` 1.18 → 1.3, then `gear.upgradeCostGrowth` 1.6 → 1.35. Canonical seed result: soft 6.58 min (delta +9.7%), hard 58.99 min (+9.2%) — both inside ±20%. `hpGrowth` and `levelExponent` were deliberately rejected: `choices.test.ts` asserts behavioral projection windows for the stage-10 boss (geared via `makeGear(5)`, and unarmed), which only hold on the baseline enemy-HP curve; weakening enemies by lowering `hpGrowth` or raising `levelExponent` breaks those behavioral assertions, and the rules forbid loosening behavioral tests.
**Trade-offs:** Upgrades are now cheaper and stronger, which inflates late-game stats; sweep seeds still spread over ~13–37 min hard wall because drop RNG couples non-linearly with the greedy policy. Canonical is the only hard assertion, so this is reported as a warning.
**Revisit:** Only if tolerance policy or sweep robustness requirements change.
**Superseded by:** "Deterministic power core: bounded RNG, bounded free grants, DPS-based swap" (Phase 3b).
